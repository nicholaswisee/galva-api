# 02. P2P Business Logic & Lifecycle Guide

> **Audience:** Domain developers and AI Agents.
> This document details the Purchase-to-Pay (P2P) lifecycle, status state machines, document numbering rules, and financial calculation formulas in `galva-api`.

---

## 1. End-to-End P2P Lifecycle Overview

The GalvaERP P2P workflow progresses through 6 sequential stages:

```
[Stage 1] Purchase Requisition (SPB / SubSPB)
   │ Internal department request for materials/items
   ▼
[Stage 2] Purchase Order — Draft (POSem / SubPOSem)
   │ Initial purchase order draft issued to supplier (POSem = "sementara")
   ▼
[Stage 3] PO Confirmation (PO / SubPO)
   │ Confirmed, finalized purchase order agreed upon with supplier
   ▼
[Stage 4] Goods Receipt (LPB / SubLPB)
   │ Physical receipt of items at warehouse (LPB = Laporan Penerimaan Barang)
   ▼
[Stage 5] AP Invoice (VoucherAP / SubVoucherAP)
   │ Account Payable invoice creation linked to Goods Receipt or PO
   ▼
[Stage 6] Vendor Payment (Bayar / SubBayar)
   │ Cash/Bank payment voucher settling AP invoices
```

## 2. Document Numbering Conventions (`Doku`)

Document numbers are automatically generated by API handlers using standard date-prefixed formats:

| Stage | Header Table | Document Format | Example | Handler Logic |
|---|---|---|---|---|
| Requisition | `SPB` | `SPB-yyyyMMdd-{seq:003}` | `SPB-20260730-001` | Daily sequence counter based on `Tgl` |
| Draft PO | `POSem` | `POS-yyyyMMdd-{seq:003}` | `POS-20260730-001` | Sequence generated on creation |
| PO Confirmation | `PO` | `PO-yyyyMMdd-{seq:003}` | `PO-20260730-001` | Sequence generated on supplier confirmation |
| Goods Receipt | `LPB` | `LPB-yyyyMMdd-{seq:003}` | `LPB-20260730-001` | Sequence generated upon warehouse intake |
| AP Invoice | `VoucherAP` | `VAP-yyyyMMdd-{seq:003}` | `VAP-20260730-001` | Sequence generated upon invoice verification |
| Payment | `Bayar` | `BAY-yyyyMMdd-{seq:003}` | `BAY-20260730-001` | Sequence generated upon disbursement |

## 3. Financial Calculation Formulas

All handlers MUST strictly enforce the following standard financial calculations for accuracy:

### 3.1 Line Item Calculations
- **Line Gross:** `LineGross = Line.Jumlah * Line.Harga`
- **Line Discount:** 
  - If percentage specified: `LineDisc = LineGross * (Line.DiscPct / 100.0)`
  - If flat amount specified: `LineDisc = Line.Disc`
- **Line Net:** `LineNet = LineGross - LineDisc`

### 3.2 Document Header Summary Calculations
- **Header Gross:** `Gross = Sum(LineGross)`
- **Header Discount:** `Discount = Sum(LineDisc) + Header.Diskon`
- **Net Subtotal:** `Net = Gross - Discount`
- **Taxable Base (DPP):** `DPP = Header.DppNilaiLain > 0 ? Header.DppNilaiLain : Net`
- **Value Added Tax (PPN):** `PPN = DPP * (Header.PpnRate / 100.0)`
- **Header Grand Total:** `GrandTotal = DPP + PPN + Header.PPnTunai`

## 4. Status State Machine & Rules (`STS` / `Sts`)

Document lifecycle states are managed via string status columns (`STS` or `Sts`):

```
       ┌──────────────┐
       │ 0 = Draft /  │
       │   Pending    │
       └──────┬───────┘
              │ Approve / Confirm
              ▼
       ┌──────────────┐
       │ 1 = Approved │
       └──────┬───────┘
              │ Receive / Fulfill
              ▼
       ┌──────────────┐
       │ 2 = Partial  │
       └──────┬───────┘
              │ Fully Processed
              ▼
       ┌──────────────┐
       │ 3 = Closed / │
       │   Completed  │
       └──────────────┘

 (Any stage can be soft-deleted if STS == 0 -> Hapus = Username|Timestamp)
```

| State Code | Meaning | Allowed Actions | Constraints |
|---|---|---|---|
| `"0"` | Pending / Draft | Update (`PUT`), Delete (`DELETE`), Approve | Modifiable only in this state. |
| `"1"` | Approved / Active | Downstream creation (e.g. create GR from PO) | Cannot be deleted or updated directly. |
| `"2"` | Partially Fulfilled | Partial receipts / partial payments allowed | Downstream document tracking. |
| `"3"` | Closed / Completed | Read-only | Fully settled / fulfilled. |

### Business Rule Violations (Domain Exceptions):
1. **Deletion Guard:** Attempting to delete a record with `STS != "0"` throws `DomainException` (`400 Bad Request` or `409 Conflict`).
2. **Upstream Fulfillment Guard:** Cannot create a Goods Receipt (`LPB`) for a PO Confirmation (`PO`) if the PO is soft-deleted (`Hapus != null`) or has `STS == "0"`.
3. **Quantity Over-receipt Guard:** Cumulative received quantity in `SubLPB.Jumlah` cannot exceed confirmed order quantity in `SubPO.JumlahKonfirm`.
